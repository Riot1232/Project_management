## 3. Суть COSMIC

COSMIC оценивает **функциональный размер** программного обеспечения по функциональным пользовательским требованиям (**FUR**). Измерение строится вокруг уникальных **функциональных процессов**, инициируемых событием и запускающей **Entry** от функционального пользователя.

Единица измерения — **COSMIC Function Point (CFP)**. Одно учитываемое логическое движение одной группы данных = **1 CFP**. Четыре типа движений:

| Тип | Название | Что измеряет |
|---|---|---|
| **E** | Entry | Группа данных поступает от functional user через границу в измеряемое ПО |
| **X** | Exit | Группа данных выходит от измеряемого ПО к functional user |
| **R** | Read | Группа данных читается из постоянного хранилища внутри границы |
| **W** | Write | Группа данных записывается в постоянное хранилище внутри границы; логическое удаление также считается W |

Размер функционального процесса: `CFP(FP) = N(E) + N(X) + N(R) + N(W)`.  
Размер измеряемого ПО: `CFP(scope) = Σ CFP(FP)` по всем уникальным процессам в согласованной области измерения. Источник: Manual v5.0, Part 1, §§4–5, Rules 10–23.

## 4. Важнейшие правила применения

1. **Scope и boundary устанавливаются до измерения.** Нельзя считать внешний API-вызов внутренним Read/Write, не определив границы.
2. **Use Case не равен Functional Process.** Один UC может содержать несколько событий/процессов; пересечения между UC не должны дублироваться.
3. **Data Group** — логический набор атрибутов об одном **Object of Interest (OOI)**, а не отдельное поле, физическая таблица или SQL-оператор.
4. Для каждого FP нужна запускающая Entry и как минимум ещё одна Exit или Write (минимум **2 CFP**).
5. Считаются **типы логических движений**, а не количество экземпляров записей, сетевых сообщений или повторных SQL-обращений.
6. Логическая обработка и алгоритмы отдельно CFP не добавляют, если не требуют новых движений данных.
7. Все предусмотренные сообщения ошибок/подтверждения в рамках одного FP обычно учитываются **одной Exit**; содержательный выходной результат может образовать отдельную Exit (Manual, Part 2, §3.4).
8. Отдельное событие по таймеру может запускать процесс через Entry от functional user «Clock», но обычное получение времени от ОС автоматически не учитывается как движение.
9. **CFP — не человеко-часы.** Для оценки трудоёмкости потребуется отдельная обоснованная модель производительности/сопоставимых проектов.

## 5. Как использовать знания в задачах T7–T9

| Задача | Что подготовить | Выход |
|---|---|---|
| **T7** | Получить подробные проверенные UC; определить scope, boundary, акторов, triggering events и уникальные FP | Реестр функциональных процессов |
| **T8** | Для каждого FP определить объекты интереса, группы данных и E/X/R/W с обоснованием | Журнал движений данных |
| **T9** | Проверить журнал, назначить каждому учитываемому движению 1 CFP, суммировать по FP и проекту | Проверяемый размер в CFP и протокол допущений |

Для конкретного процесса «Создание заявки» потенциально понадобятся Entry данных заявки, Read справочника категорий, Write заявки и Exit результата; однако наличие каждого движения подтверждается **не общими предположениями о сервис-деске, а утверждёнными FUR**. Пример не является расчётом A2.
